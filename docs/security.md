# Security review (Phase 5)

This is the Phase 5 hardening deliverable: a review of the system as built,
what was verified, what is accepted by design, and what is deliberately left
for later. It describes the running code, not aspirations.

Scope: the Express API (`backend/`), the React client (`frontend/`), the
PostgreSQL schema (`database/migrations/0001_core_schema.sql`) and their
configuration.

## 1. Authentication and sessions

- **Passwords** are hashed with Argon2id (`@node-rs/argon2`, OWASP
  parameters) in `src/lib/password.ts`. Plaintext is never stored, logged or
  audited. Unknown-email logins still run a dummy verification, so response
  timing does not reveal whether an account exists.
- **Sessions** are HS256 JWTs (`jose`) in an `HttpOnly`, `SameSite=Lax`
  cookie with a fixed max age; `Secure` is set in production
  (`src/lib/cookies.ts`). Logout clears the cookie.
- **Deactivation/role changes** take effect on the next request: every
  guarded request re-reads the account from the database
  (`src/middleware/auth.ts`), so a stolen-but-valid cookie stops working the
  moment the account is deactivated.
- Verified by: auth integration tests (login, logout, me, CSRF) plus live
  smoke tests on every phase.

Accepted by design: sessions are stateless; there is no server-side session
revocation list. The database check on every request is the control.

## 2. CSRF

Signed double-submit cookie (HMAC over a random token, `src/lib/csrf.ts`).
Every state-changing request must echo the readable `ca_session_csrf` cookie
in `X-CSRF-Token`; `SameSite=Lax` adds defence in depth. Verified in the
middleware tests.

## 3. Authorization and scoping

Central rule: a resource is reached through the caller's own scope, and
everything out of scope answers **404**, never 403, so existence does not
leak.

| Role | Scope |
| --- | --- |
| admin | departments, classes, staff accounts, system reports, audit log |
| hod | own department only (classes, assignments, reports, class drill-down) |
| faculty | actively assigned classes only (rosters, sessions, reports) |
| student | own enrollments and own records only (today, history) |

Scope helpers live in `src/services/classes.ts` (`getClassForFaculty`,
`getClassForDepartment`) and every route resolves them before touching data.
Integration tests cover cross-role and cross-department attempts (403 on
wrong role, 404 out of scope).

## 4. Input validation and injection

- All bodies, params and query strings are parsed with zod schemas
  (`src/middleware/validate.ts`); report ranges additionally reject
  `from > to` and spans over 366 days, and audit paging is capped at 100
  rows per page.
- Every SQL statement uses parameter placeholders; the only dynamic SQL is
  the audit filter builder, which only ever concatenates fixed fragments with
  generated `$n` placeholders (`src/services/audit.ts`).
- JSON bodies are limited to 100 kB.
- Invalid UUID path segments answer 400 before reaching the database.

## 5. OTP handling

- OTPs are 6 digits, expire after 10 minutes, allow 5 attempts per
  generation, and are regenerated by faculty only.
- Stored exclusively as HMAC-SHA-256 with server-side `OTP_PEPPER`; the raw
  code is returned exactly once, to the faculty member who generated it.
- `otp_attempts` rows record success/failure, IP and time — never the code —
  and integrity tests assert codes never reach the audit log.
- The attempt-count window uses the database clock, so device clock skew
  cannot reset lockouts.

## 6. Rate limiting (added in Phase 5)

| Surface | Limit | Key | Notes |
| --- | --- | --- | --- |
| Login | 10 failures / 15 min | IP | Successful logins are not counted. |
| Student self-marking | 30 failures / 15 min | Student id | Successful marks not counted, so a whole class on one campus IP is fine. In addition to the per-OTP 5-attempt cap. |
| Registration submissions | 30 requests / 15 min | IP | Phase 6 public write endpoint; every submission counts. A coarse spam guard — the real duplicate guard is the partial unique index on pending email / register number. |

Both use `express-rate-limit` with `standardHeaders: 'draft-8'` and return a
plain 429 JSON error. The marking limiter runs after authentication, so the
key is the account, not the network. Behind the free-tier proxy chain `req.ip`
may be a CDN address (see `docs/deployment-free.md`), which makes the
IP-keyed limits coarser, not weaker than their cap.

Accepted by design: the limiter store is in-process memory. This is correct
for the single-instance deployment this project targets; a multi-instance
deployment must switch to a shared store (e.g. Redis) — noted as a
follow-up.

## 7. Audit trail

- Every sensitive mutation is audit-logged with actor, entity, before/after
  snapshots and IP; OTP codes and password material never appear.
- The Phase 5 admin view (`GET /api/admin/audit`) is admin-only, read-only,
  filtered and paginated. Rows are never updated or deleted by the
  application.
- Failed logins with unknown emails are recorded with a null actor. Public
  registration submissions (`registration.submit`, Phase 6) are also logged
  with a null actor; the student's chosen password appears only as its
  Argon2id hash in the audit-free request row.

## 8. Transport, headers and secrets

- TLS verification is enabled everywhere (`sslmode=verify-full` with the
  pinned Supabase CA); no code path disables certificate checks.
- Since Phase 5 every API response sets `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`,
  `Cross-Origin-Resource-Policy: same-origin` and `Cache-Control: no-store`
  (`src/app.ts`). Verified live.
- Secrets (`JWT_SECRET`, `OTP_PEPPER`, `DATABASE_URL`) live only in
  git-ignored `backend/.env`; only placeholders ship in `.env.example`. The
  process refuses to start without the JWT secret and OTP pepper.
- CORS is intentionally absent: the frontend talks to the API through the
  same origin (Vite proxy in development, reverse proxy in production), so
  no cross-origin grant exists to misconfigure.

## 9. Database hardening

- RLS is enabled on every table and `anon`/`authenticated` grants are
  revoked, so Supabase's PostgREST cannot read or write data even if the
  anon key leaks.
- Application connections use a dedicated database role; the API which is
  public (login, health) is the only thing reachable without a session.
- CHECK constraints enforce domain honesty (one session per class per date,
  close metadata consistency, manual marks always attributed).

## 10. XSS / client-side

- React escapes all interpolated values; the app never uses
  `dangerouslySetInnerHTML`.
- The audit view renders snapshots inside a `<pre>` via
  `JSON.stringify`, not as HTML.
- The session cookie is `HttpOnly`, so client-side script cannot read it.

## 11. Dependency review (October 2026)

`npm audit` (runtime and full trees) reports **0 vulnerabilities** for both
`backend/` and `frontend/` at the time of writing. No new dependency was
added in Phase 5 — the rate limiting reuses `express-rate-limit`, and the
security headers are set manually.

## 12. Verification performed for this review

- `npm run build` (backend and frontend), `npm run typecheck`, `npm run lint`.
- Full Vitest suite against a real database (65 passed / 2 skipped),
  including the new reports, audit and rate-limit scenarios.
- Live smoke against the running dev stack: 47 checks covering the morning
  flow, every report endpoint, the audit view, the 31st-blocked marking
  attempt and the security headers.
- Manual review of the routes, middleware, services and migration listed
  above.

## 13. Accepted limitations and follow-ups

1. **In-memory rate limits** — single-instance assumption (see §6).
2. **No MFA / password-reset email** — out of scope for the student-project
   phase plan; faculty/admin reset passwords manually.
3. **Stateless JWT sessions** — revocation is via account deactivation
   (effective next request). Acceptable for this deployment.
4. **Audit log growth** — no retention policy yet; `created_at` is indexed
   and the admin view paginates.
5. **Reports read live tables** — fine at college scale; if data grows,
   move aggregation into materialized views behind the same endpoints.
